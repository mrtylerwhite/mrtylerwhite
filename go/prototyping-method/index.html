The problem

Building got cheap. So did building the wrong thing.

AI can spit out a screen in seconds. Most designers use that to make more mockups, faster, and still walk into review with nothing but a vibe.

It will hand you a wrong answer with total confidence. It makes up copy, invents edge cases and suggests things that would never work in your product. Present that and you look sloppy, fast.

The designers getting ahead use the speed for something else: finding out what's wrong before anyone else sees it, then showing up with a prototype and a number.

The method

Five steps to a prototype you can defend.

The tool matters less than the order. Context, exploration, real testing, the business case, then polish.

1.

Load context first

Connect Claude to your GitHub repo and feed it the PRD, notes and screenshots before you ask for anything. Then tell it to wait.

2.

Explore 4 to 5 directions

Separate threads, one prompt. You're looking for what breaks, so two of them usually die right away. That's the point.

3.

Build the risky part in code

Anything with real logic gets a quick working version in Cursor. That's where the problems mockups hide show up.

4.

Put a number on it

Run the ROI step on the direction that survived, so your review starts with what the change is worth instead of how it looks.

5.

Polish and hand off

Once the logic holds up, move to Figma, line it up with the design system and hand engineering something that already works.
